# Future Prototype Acceptance Criteria — not an authorization

## Stage 0: mandatory approval preflight
An explicit project owner record AP-01 must define mock-only scope, named developer, isolated project/workspace and branch, zero external spend, approved source list and independent reviewer. A distinct AP-02 must authorize read-only access to each exact approved file. Missing either means `HOLD_NOT_APPROVED`; no copying files to another workspace or implementation. G17 and G18 stay HOLD until separately signed. A prototype is never a production release.

## Stage 1: implementation design checks (only after approval)
- Eleven modules A00–A10 and five adapters N01–N05, or equivalent mapping explicitly approved before development.
- Versioned records, immutable source IDs, source access and redistribution rights separated, `NOT_CHECKABLE` distinct from false or true.
- Topic lock preserves subject/object and `alleged`/forecast qualifiers; time-sensitive material defaults HOLD on missing validated issue dates.
- Failed or unverified findings (F-190), inaccessible R052, and K029–K031 hypotheses never support positive retention/scientific claims.
- No hidden source revision, restricted output, unauthorized API use or publication.
- All sample narratives fictional test data clearly labelled `RESEARCH_ONLY_NOT_PUBLISHABLE`.

## Stage 2: software QA, not audience science
- Frozen QA-001…QA-036 detailed expectations preserved from the existing architecture worker.
- Expected future pass: **36/36 actually executed automated fixture checks** with positive and negative cases and attached per-ID actual outputs. Today **0/36 executed**.
- Any critical safety/source-rights falsification, invented quote, stale hazard, misleading event reconstruction, unsigned release or topic-reference change must fail the test run and force repair.
- Five distinct synthetic niche demonstration runs plus a multi-overlay stress case.
- No calls to live internet, paid provider, YouTube/analytics or real external accounts. Test run must be deterministic/reproducible from pinned code commit and fixture revision.
- Record any failures openly; do not report PASS based on a plan or a self-written rubric alone.

## Stage 3: technical independent review
- Named non-author reviewer or Codex checks schema invariants, code/fixture accuracy, source separation, prompt injection safety and evidence gates on the actual built artifact.
- A developer's self-QA cannot be called independent. Independent review result must include findings, severity, change/repair log and post-fix retest receipts.
- A clean technical prototype **still does not validate YouTube watch-time, human comprehension, production factuality or untested scientific formulas**.

## Stage 4: owner acceptance
Result choices: `ACCEPT_INTERNAL_MOCK_PROTOTYPE_ONLY`, `RETURN_FOR_REPAIR`, `HOLD`. None can clear production SKILL.md, third-party content rights, real audience experiments or publication. Production G18 is a new, distinct decision after broader work.

## Non-negotiable preserved baselines
T01–T13 scientific validation designs: **0/13 executed**. Architecture software fixtures: **36 DESIGN_ONLY** until actual future implementation. No original historical S/F/R/V/K/EDU claims, research SHA ledgers or ZIPs may be rewritten to make acceptance appear to pass.
